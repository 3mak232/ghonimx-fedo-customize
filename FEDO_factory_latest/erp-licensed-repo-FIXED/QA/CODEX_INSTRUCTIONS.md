# تعليمات Codex — كيف تراجع وتُبلغ عن الأخطاء داخل المستودع

هذا الملف يجعل نتائج QA جزءًا من دورة التطوير نفسها، بدل نقلها يدويًا.

## 1) قبل أي مراجعة

```sh
git fetch origin
git checkout <الفرع-المطلوب-مراجعته>
git log -1 --oneline          # سجّل رقم الـcommit في التقرير
```

## 2) التشغيل الكامل (قاعدة محلية فارغة — لا إنتاج ولا بيانات عميل)

```sh
cd FEDO_factory_latest/erp-licensed-repo-FIXED/erp-kit/05-tests
npm install                       # jsdom لاختبار الواجهة (مرة واحدة)
./run_all_local.sh --keep
```

- السكربت يُنشئ `fedo_factory_test`، يُحمّل shim + الأساس + v1→v5 مرتين، lockdown،
  ثم يشغّل كل اختبارات SQL، ثم اختبار التزامن على قاعدة `fedo_roll_v5_race`،
  ثم اختبار الواجهة على jsdom، ثم يفحص عدادات lockdown.
- أي فشل يخرج بكود غير صفري ويطبع آخر 25 سطرًا من السبب.
- `--keep` يُبقي قاعدة الاختبار للتحقيق؛ بدونها تُحذف.

تشغيل جزئي:

```sh
psql -v ON_ERROR_STOP=1 -d fedo_factory_test -f factory_roll_ledger_v5_test.sql
node factory_ui_smoke_test.js
python3 factory_roll_v5_race_test.py
```

## 3) تسجيل التقرير

1. أنشئ مجلدًا: `QA/<DATE>_<PHASE>/` مثل `QA/2026-11-08_PHASE2/`.
2. احفظ مخرجات التشغيل كاملة (بدون تعديل) داخل المجلد.
3. اكتب `CODEX_REPORT.md` بالصيغة التالية **حرفيًا** (الأقسام الأربعة إلزامية):

```md
# تقرير Codex — <المرحلة>
commit: <sha>
branch: <name>
environment: PostgreSQL <ver> / shim / local only

## القرار
READY | NOT READY

## ما نجح
| الاختبار | النتيجة | الدليل |
|---|---|---|

## ما فشل
| Bug ID | الخطورة | الوحدة | الوصف | الدليل (ملف:سطر) | الإصلاح المقترح |
|---|---|---|---|---|---|
| BUG-101 | HIGH | ... | ... | ... | ... |

## لم يُنفذ
| الاختبار | السبب |
|---|---|
```

## 4) قاعدة إلزامية للتقارير

- كل بند فاشل **يجب** أن يحمل: معرّف `BUG-xxx`، خطورة (HIGH/MEDIUM/LOW)، ملفًا وسطرًا، وخطوات إعادة إنتاج قابلة للتنفيذ.
- لا تُدرج بيانات عميل أو أسرارًا أو مفاتيح في التقرير أو السجلات.
- إن كان الفشل في **اختبار** لا في الكود، وضّح ذلك صريحًا واقترح تعديل الاختبار.
- لا تُعدّل ملفات `erp-kit/01-database/*.sql` أو `erp-kit/03-frontend/*.js` من جهة QA؛ التعديل مسؤولية المطوّر.

## 5) كيف يصل التقرير للمطوّر

- **الطريقة المفضلة:** افتح Pull Request على الفرع نفسه يضيف مجلد `QA/<DATE>_<PHASE>/` فقط.
- بديل: ارفع الملفات مباشرة على نفس الفرع (commit مستقل باسم `qa: phase N report`).
- المطوّر يعالج كل `BUG-xxx` ثم يكتب في نفس `CODEX_REPORT.md` قسمًا إضافيًا:

```md
## رد المطور
| Bug ID | الحالة | commit الإصلاح | الاختبار الذي يثبت الإصلاح |
|---|---|---|---|
```

## 6) معايير قبول المرحلة (Definition of Done)

المرحلة لا تُعتبر مكتملة إلا إذا تحققت **كل** النقاط:

1. `./run_all_local.sh` ينجح كاملًا من قاعدة فارغة.
2. migration الجديدة تعمل مرتين بلا خطأ (idempotency).
3. `lockdown 0/0/0` بعد التطبيق.
4. اختبار صلاحيات لكل دور جديد أو دالة جديدة (`admin/store/sales/accountant/custom/anon`).
5. اختبار idempotency لكل RPC كتابة جديدة (نفس المفتاح = نفس النتيجة، مفتاح مختلف ببيانات مختلفة = رفض).
6. اختبار توازن القيود المحاسبية المتأثرة + `rebuild_journal` يعطي نفس النتيجة.
7. معادلة المخزون: مجموع أرصدة الرولات = رصيد FEDO قبل وبعد كل عملية.
8. الواجهة: مسار جديد في `NAV` + صلاحية في `P` + تحقق في `factory_ui_smoke_test.js`.
9. الملفات الممنوعة على `anon`/`authenticated` (الجداول الداخلية والدوال الخاصة) تبقى مسحوبة.

## 7) خارج نطاق QA المحلي (يحتاج staging حقيقي)

- Edge Functions، الترخيص، `license-sync`، النسخ الاحتياطي/الاستعادة السحابي.
- المتصفح الحقيقي والموبايل وRTL المرئي والأداء.
- التزامن علىSupabase (اختبارنا محلي على PostgreSQL فقط).
- أي بيانات عميل حقيقية.
